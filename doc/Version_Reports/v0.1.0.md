## Core: Sistema de Modificadores y Parámetros

### 🔧 Visión General

El sistema de modificadores actúa como el motor de cambio del juego, permitiendo que eventos y decisiones alteren los parámetros de las provincias y del jugador. Se implementó bajo un modelo de "libro de contabilidad" que desglosar todos los cálculos para mayor transparencia y debugging.

### 📊 ModifierService: El Libro de Contabilidad

**Responsabilidad**: Generar proyecciones de cambios de parámetros basadas en modificadores activos.

**Estructura de Datos Principal**:
```
Dictionary<string, Dictionary<SOR_Enums.Parameters, ChangeReport>>
    └─ Identificador (Provincial ID o "Global")
        └─ Parámetro (Influence, Popularity, etc.)
            └─ ChangeReport (reporte completo de cambios)
```

**ChangeReport** contiene:
- `changes`: Lista de cambios individuales (quién/qué provocó cada cambio)
- `totalBase`: Suma de todos los modificadores directos
- `finalValue`: Valor final después de aplicar fórmulas

**Flujo de Generación de Proyecciones**:

1. **Inicialización Obligatoria**: Se crean reportes para parámetros que **no dependen de modificadores** (efectos pasivos)
   - Parámetros globales: Influence, Fame, Determination
   - Parámetros provinciales: Popularity (crecimiento pasivo)

2. **Carga de Modificadores Activos**: Se itera sobre cada modificador activo y se añaden sus valores a los reportes correspondientes
   - Modificadores globales se añaden a "Global"
   - Modificadores provinciales se distribuyen según su configuración

3. **Resolución de Fórmulas**: Se aplican cálculos especiales que alteran `finalValue`

### 🧮 Sistema de Fórmulas

Las fórmulas permiten que ciertos parámetros se calculen dinámicamente basándose en el estado actual del juego.

#### Fórmula 1: Efecto Red (Crecimiento Pasivo de Popularity)
```
finalValue = totalBase + (popularity * 0.01)
```
- Se aplica **solo a parámetros Popularity provinciales**
- Representa el crecimiento orgánico sin intervención externa
- Intensidad: 1% de la popularidad actual

#### Fórmula 2: Alineados (Estabilidad)
```
stabilityFactor = (50 - stability) / 100
stabilityBonus = totalBase * stabilityFactor
finalValue = totalBase + stabilityBonus
```
- Se aplica **solo si hay modificadores activos** (`totalBase != 0`)
- A menor estabilidad, mayor multiplicador de alineados
- Representa la facilidad de radicalizar cuando hay inestabilidad

### 🎮 ModifierManager: Orquestador de Cambios

**Responsabilidades Principales**:

1. **Gestión del Caché de Modificadores**: Mantiene un Dictionary de modificadores activos indexados por `customId`

2. **Lectura e Integración de Nuevos Modificadores** (`ReadModifier`):
   - Clona las instrucciones del modificador (para evitar mutaciones en el original)
   - Inicializa el modificador con `ActiveModifier.Initialize()`
   - Genera un ID único si el modificador es nuevo o actualiza el existente si ya existe en esas provincias
   - Valida expiración y refresca proyecciones

3. **Dos Eventos Clave**:
   - `OnModifiersChanged`: Se dispara cuando un modificador se añade/actualiza/elimina (antes del tick diario)
   - `OnModifiersApplied`: Se dispara después de aplicar el tick diario

4. **Validación de Decisiones** (`IsDecisionValid`):
   - Comprueba si una decisión tiene al menos una provincia válida donde aplicarse

### 🏷️ ActiveModifier: Componente Ejecutable

**Estructura**:
- `instructions`: Las instrucciones del modificador (qué parámetros cambiar, en qué provincias, durante cuánto tiempo)
- `expirationDate`: Cuándo expira este modificador

**Inicialización (Initialize)**:

1. **Procesamiento de Flags**: Convierte flags especiales en IDs reales de provincias
   - `[all]` / `[all_fragmented]`: Todas las provincias
   - `[all_player_here]` / `[all_player_here_fragmented]`: Solo donde está el jugador
   - `[all_player_away]` / `[all_player_away_fragmented]`: Donde no está el jugador
   - `[player_here]` / `[player_away]`: Una provincia aleatoria (sin repetición)

2. **División de Valores (_fragmented)**: 
   - Si se usa flag "fragmented", se divide el valor del modificador entre el número de provincias destino
   - Ejemplo: Un modificador de +50 popularity con `[all_player_here_fragmented]` en 3 provincias = +16.67 en cada una

3. **Cálculo de Expiración**:
   - `durationDays = -1` → Permanente (hasta fin del juego)
   - `durationDays > 0` → Expira en `CurrentAbsDay + durationDays`

### 🔐 IDs Dinámicas y Prevención de Sobrescrituras

**Problema Original**: Si el mismo modificador se aplicaba a diferentes provincias, se sobrescribían mutuamente.

**Solución**: 
- Se genera un `customId` único basado en:
  - ID de la decisión/modificador base
  - Provincias específicas a las que se aplica
- `GenerateUniqueId()` crea una firma única: `{decisionId}_{provincesHash}`

**Comportamiento**:
- Si el `customId` ya existe → Se actualiza (refresca duración, recalcula expiración)
- Si el `customId` es nuevo → Se crea un nuevo modificador

### 📊 Parámetros del Sistema

**Parámetros Globales** (afectan al jugador):
- `Influence`: Poder político acumulado
- `Fame`: Reputación pública (-100 a 100)
- `Determination`: Voluntad de continuar (0 a 100)

**Parámetros Provinciales** (por provincia):
- `Popularity`: Soporte popular general (0 a infinito)
- `Aligned`: Número de ciudadanos alineados con la causa (0 a population)
- `Affiliates`: Miembros activos de la organización (0 a population)
- `Stability`: Estabilidad política provincial (0 a 100)

### 🛡️ Lógica de Cap (Límite Máximo)

Aunque no se describe en detalle en los scripts, el sistema está preparado para:
- Ocultar feedback de modificadores en la UI si un parámetro ha alcanzado su límite
- Validar que los modificadores no superen los límites establecidos

## 📅 Sistema de Tiempo y Calendario

### 🕐 Migración a DateTime: TimeManager Refactorizado

**Estado Anterior**: Sistema de días absolutos desconectado del calendario real.

**Estado Actual**: Sistema completamente integrado con calendarios reales y mapas específicos.

#### Estructura de Datos: TimeManagerData

```csharp
public class TimeManagerData {
    public double minute = 0;      // [0, 60)
    public int hour = 0;           // [0, 24)
    public int day = 0;            // [1, daysInMonth]
    public int month = 0;          // [1, monthsInYear]
    public int year = -1;          // -1 = usa fecha de inicio del mapa
}
```

#### SO_CalendarConfig: Configuración de Calendario

**Responsabilidades**:
1. **Definición de Meses**: Array de `MonthData` con nombre y días
2. **Fechas Especiales**: `startDate` (formato "DD/MM/YYYY")
3. **Cálculos Relativos**: Convierte fechas reales a "días absolutos" del juego

**Métodos Clave**:

- `ApplyStartDateToData()`: Inicializa TimeManagerData con la fecha de inicio del mapa
- `GetRelativeAbsDay(day, month, year)`: Convierte una fecha a "días desde el inicio del juego"
  - Compensa el offset del startDate automáticamente
  - Ejemplo: Si startDate es 01/01/2024 y consultas 02/01/2024 → retorna 1
- `GetDaysInMonth()`: Respeta años bisiestos y estructura de meses personalizada
- `IsLeapYear()`: Validación de años bisiestos

#### TimeManager: Orquestador del Tiempo

**Flujo de Tiempo**:

```
Update() → CalculateTime()
    ├─ _data.minute += Time.deltaTime * _TIMESCALE
    ├─ Si minute >= 60: OnHourPassedEvent
    └─ Si hour >= 24: ProcessDayPass()
        ├─ OnDayPassedEvent
        ├─ Si day > maxDays: ProcessMonthPass()
        │   └─ OnMonthPassedEvent
        └─ Si month > 12: ProcessYearPass()
            └─ OnYearPassedEvent
```

**Eventos Públicos**:
- `OnHourPassedEvent`: Cada hora en tiempo de juego
- `OnDayPassedEvent`: Cada día (dispara el tick diario)
- `OnMonthPassedEvent`: Cambio de mes
- `OnYearPassedEvent`: Cambio de año
- `OnGameTimePaused` / `OnGameTimeReanudated`: Control de pausa
- `OnGameTimeScaleChanged`: Cambio de velocidad

**Control de Velocidad**:
- `_TIMESCALE`: Horas de juego por segundo real (default: 300)
- Array de escalas: [0 (pausa), 1x, 2x, 3x]
- Cambio dinámico durante el juego

### 🎯 Integración con Eventos

Cada evento ahora tiene:
- `triggerDate` (formato "DD/MM/YYYY"): Fecha en la que puede comenzar a aparecer
- `triggerHour`: Hora específica en la que se muestra (0 = cualquier hora)

**Cálculo de Disponibilidad**:
```csharp
if (e.eventStorage.triggerDate != null && valido) {
    triggerDateOk = _timeManager.CurrentAbsDay >= _mapTemplate.calendarConfig
        .GetRelativeAbsDay(day, month, year);
}
```

## 🎪 Sistema de Eventos y Decisiones

### 📋 EventManager: Orquestador de Eventos

**Concepto Central**: Una **EventQueue (Cola de Eventos)** que mantiene track de qué eventos se deben mostrar en el día actual.

#### Flujo de Eventos

1. **Generación Diaria** (`HandleEventRoll`):
   - Se ejecuta cada día (trigger: `OnDayPassedEvent`)
   - Filtra eventos elegibles basándose en múltiples condiciones
   - Realiza un roll aleatorio (30% de probabilidad por defecto)

2. **Filtrado de Elegibilidad**:

```csharp
var eligibleEvents = eventsBatery.Where(e => {
    // Condición 1: Cooldown
    bool cooldownOk = IsAvailable(status.availableDate, today);
    
    // Condición 2: Eventos únicos
    bool uniqueOk = e.isUnique ? !status.hasTriggered : true;
    
    // Condición 3: Decisiones válidas
    bool hasValidDecisions = e.decisions
        .Any(d => IsDecisionValid(d));
    
    // Condición 4: Fecha de trigger
    bool triggerDateOk = today >= triggerDate;
    
    return cooldownOk && uniqueOk && hasValidDecisions && triggerDateOk;
});
```

#### Sistema de Cooldown Multinivel

El sistema implementa tres niveles de cooldown:

1. **Cooldown Individual por Evento**:
   - Definido en `EventStorage.cooldownDays`
   - Si es ≤ 0, usa el default del manager (_DEFAULT_EVENT_COOLDOWN = 7 días)
   - Se resetea cuando se selecciona una decisión del evento

2. **Cooldown Global**:
   - Previene que múltiples eventos se disparen en días consecutivos
   - Default: 3 días (_DEFAULT_GLOBAL_COOLDOWN)
   - Se aplica después de cualquier decisión

3. **Eventos Únicos** (`isUnique`):
   - Solo pueden dispararse UNA VEZ en toda la partida
   - Se marca `hasTriggered = true` después de completar

#### EventQueue y Persistencia

```csharp
private Dictionary<string, SO_Event> _currentDayEventQueue = new();
```

- **Propósito**: Almacenar eventos que están "activos" en el día actual
- **Sincronización**: Se guarda en `GameData.eventData.activeEventQueue` al hacer save
- **Uso**: La UI itera sobre esta cola para mostrar eventos

### 🎛️ Toma de Decisiones (Decision System)

#### SO_Decision: Estructura de Decisión

```csharp
public class SO_Decision {
    public string decisionId;
    public string decisionTitle;
    public string decisionDescription;
    public bool skipIfNoAviableProvinces;
    public ModifierInstructions[] modifiersArray;
}
```

**Validación OnValidate()**:
- Sincroniza automáticamente la `decisionId` en todos los modificadores asociados
- Genera `customId` automáticamente si está vacío: `{decisionId}_MOD_{index}`

#### SO_Event: Envoltorio de Evento

```csharp
public class SO_Event {
    public SOR_Enums.EventStorage eventStorage = new();
}
```

Contiene el `EventStorage` (ver SOR_Enums):
- `eventId`, `title`, `description`
- `category` (Generic, Political, Economic)
- `thumbnail`: Imagen del evento
- `isUnique`: ¿Solo se dispara una vez?
- `cooldownDays`: Días de espera después de completar
- `triggerHour`: Hora específica de aparición
- `triggerDate`: Fecha de disponibilidad
- `decisions`: Array de decisiones disponibles

#### Flujo de Decisión (TriggerDecision)

```
1. Iterar sobre cada modifier en decision.modifiersArray
   └─ Llamar a ModifierManager.ReadModifier()
       └─ Se añade/actualiza el modificador activo

2. Marcar evento como disparado: status.hasTriggered = true

3. Aplicar cooldown custom (o default si < 0)
   └─ status.availableDate = CalculateFutureDate(cooldownDays)

4. Aplicar cooldown global
   └─ data.eventData.globalAvailableDate = CalculateFutureDate(3)

5. Limpiar cola: Remove(eventId)

6. Invocar: OnDecisionSelected
```

#### Validación de Decisiones

`ModifierManager.IsDecisionValid()`:
- Verifica que al menos una provincia sea un destino válido para los modificadores de la decisión
- Si `skipIfNoAviableProvinces` es true y no hay provincias válidas → se oculta la decisión

## 🖥️ UI & UX (Feedback Visual)

### 📊 GameGlobalParameters_ui: Panel de Parámetros Globales

**Responsabilidad**: Mostrar el estado actual de los parámetros globales y el feedback de modificadores.

#### Secciones Mostradas

**Parámetros Actuales**:
- Influence (formato: "N0" → "1,234,567")
- Total Popularity (suma de todas las provincias)
- Total Aligned (porcentaje: "45.32 %")
- Total Affiliates (total acumulado)
- Fame ("-100% a +100%")
- Determination ("0% a 100%")

**Feedback de Modificadores**:
- Reporte de cambios de Influence/Fame/Determination (globales)
- Reporte de cambios de Popularity/Aligned/Affiliates (provinciales)

#### Visualización de Valores

Cada valor de modificador muestra:
- `+ 50.23` si es positivo
- `- 25.10` si es negativo
- `0` si no hay cambios

#### Actualización de UI

Se actualiza en dos momentos:
1. `OnModifiersChanged` → Cambios inmediatos en modificadores
2. `OnGameInitialized` → Carga inicial al comenzar

Ambos eventos disparan `UpdateUI()` que refresca todos los textos.

### 🎪 EventUiController: Gestor de la UI de Eventos

**Responsabilidad**: Mostrar eventos y permitir la selección de decisiones.

#### Componentes Visuales

- `eventTitle`: Título del evento
- `eventDescription`: Descripción larga
- `eventThumbnail`: Imagen
- `decisionContainer`: Contenedor padre de botones de decisión
- `decisionPrefab`: Prefab de botón reutilizable

#### Filtrado de Decisiones Válidas

Antes de mostrar el evento, se filtran decisiones:
```csharp
var validDecisions = _event.eventStorage.decisions
    .Where(d => _modifierManager.IsDecisionValid(d))
    .ToArray();
```

Si no hay decisiones válidas:
- Se remueve automáticamente de la cola
- No se muestra la UI

#### Control de Tiempo e Input

Cuando aparece un evento:
1. Pausa el tiempo: `_timeManager.PauseReanudeTime(false)`
2. Bloquea input de velocidad: `SetTimeInputActive(false)`
3. Bloquea la UI de interfaz: `_interfaceCanvasGroup.interactable = false`

Cuando se cierra:
1. Reanuda el tiempo
2. Activa input de velocidad
3. Reactiva UI

#### Detección de Hora de Evento

`CheckForHourEvent()`:
- Se ejecuta cada hora (trigger: `OnHourPassedEvent`)
- Busca el primer evento con `triggerHour` igual a la hora actual
- Si `triggerHour <= 0` → se muestra en cualquier hora

#### Limpieza de Decisiones Obsoletas

Después de seleccionar una decisión:
1. Se invoca `OnDecisionSelected`
2. Se destruyen todos los GameObject de decisiones
3. Se vuelve a ejecutar `CheckForHourEvent()` por si hay más eventos a la misma hora

## 🎮 Flujo de Juego

### 🎬 GameInitializer: Punto de Entrada

**Responsabilidad**: Orquestar la inicialización de todos los sistemas principales.

#### Método Initialize(bool isNewGame)

```csharp
1. Obtener referencias a managers principales:
   └─ ProvinceManager, EventManager, TimeManager

2. MapDynamicInitializer.Initialize(currentMap)
   └─ [Excluido de documentación: generación de mapa]

3. _provinceManager.Init(currentMap)
   └─ Inicializa todas las provincias

4. _eventManager.Init(currentMap)
   └─ Carga los eventos del mapa

5. _timeManager.Init(currentMap.calendarConfig)
   └─ Aplica la fecha de inicio del mapa

6. Si es new game:
   └─ Bloquea input de tiempo
      (el jugador no puede cambiar velocidad en partida nueva)

7. Marcar como inicializado: IsInitialized = true

8. Invocar: OnGameInitialized
   └─ Despierta otros sistemas que estaban esperando
```

### 📊 ModifierManager: Inicialización Post-Game

En el `Start()` del ModifierManager:

```csharp
1. Si GameInitializer ya está inicializado:
   └─ Ejecutar Init()
   
2. Si no:
   └─ Esperar a OnGameInitialized

3. En Init():
   ├─ Cargar modificadores activos del save (GameData)
   ├─ Ejecutar CheckModifiers() (validar expiración)
   ├─ Refrescar proyecciones inmediatamente
   └─ Registrarse a eventos:
       ├─ SaveSystem.OnCallSave → SyncToData
       └─ TimeManager.OnDayPassedEvent → ApplyDailyTick
```

### 🔄 Tick Diario (ApplyDailyTick)

Cuando pasa un día en el juego:

```csharp
1. TimeManager.OnDayPassedEvent invoca ApplyDailyTick

2. ModifierManager ejecuta:
   ├─ CheckModifiers()
   │  └─ CheckModifiersExpiration() + CalculateModifierValue()
   ├─ ModifierManager.ApplyDailyTick invoca OnModifiersApplied
   │  └─ ParameterController.UpdateGlobalParameters()
   │     ├─ ComputeProvincialTotals()
   │     ├─ OnParametersUpdated.Invoke()
   │     └─ CheckGameOverConditions()
   
3. EventManager.HandleEventRoll() ejecuta:
   ├─ Filtra eventos elegibles
   ├─ Roll aleatorio (30% base)
   └─ Si éxito: Añade evento a la queue

4. TimeManager detecta cambios de mes/año
   └─ Invoca OnMonthPassedEvent / OnYearPassedEvent
```

### 🏁 Condiciones de Victoria/Derrota

Se evalúan en `ParameterController.CheckGameOverConditions()`:

**DERROTA**:
- `Determination <= 0` → El jugador abandona
- `Fame <= 0` → La causa es completamente desacreditada

**VICTORIA**:
- `Aligned >= (Total Population * 0.5)` → 50% de ciudadanos alineados
- **AND** `Influence >= 5000` → Suficiente poder político para tomar el control

### 💾 Sistema de Guardado

**SaveSystem.OnCallSave** dispara sincronización:
- `ModifierManager.SyncToData()` → Guarda `activeModifiers` en JSON
- `EventManager.SyncToData()` → Guarda `activeEventQueue` en JSON
- TimeManager se sincroniza automáticamente (GameDataService)
- ParameterController se sincroniza automáticamente (su data es referenciada por GameDataService)

## 📝 Resumen Técnico de Cambios Principales

| Componente | Cambio | Impacto |
|---|---|---|
| **ModifierService** | "Libro de contabilidad" con ChangeReport | Transparencia total en cálculos |
| **ModifierManager** | IDs dinámicas + validación de expiración | Modificadores no se sobreescriben |
| **ActiveModifier** | Sistema de Flags + división de valores | Aplicación flexible de modificadores |
| **TimeManager** | Migración a sistema de calendario real | Fechas consistentes entre mapas |
| **SO_CalendarConfig** | Calendarios personalizables por mapa | Flexibilidad para diferentes épocas |
| **EventManager** | EventQueue + cooldown multinivel | Control preciso de frecuencia de eventos |
| **SO_Event/Decision** | Integración de triggerDate y triggerHour | Eventos ligados al tiempo del juego |
| **EventUiController** | Filtrado de decisiones válidas | Solo se muestran opciones realizables |
| **ParameterController** | Validación de condiciones de Victoria/Derrota | Fin de juego automático |
